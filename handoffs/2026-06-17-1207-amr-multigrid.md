# Handoff: Adaptive Mesh Refinement + Geometric Multigrid

## Goal / why this matters

`MatrixFreeOperators.jl` is single-level uniform Cartesian today. Two `DESIGN.md`
§9 requirements (items 3–4) are unbuilt: **AMR** (adaptive resolution) and
**geometric multigrid** (a solver). They share machinery — a grid *hierarchy* +
restriction `R` / prolongation `P` transfer operators — so build them together to
avoid deriving the transfer stencils twice. Decision: build **AMR first**; MG
falls out of the same hierarchy.

A full architecture + phased roadmap already exists at
`~/.claude/plans/lets-start-work-on-swift-quilt.md` — this doc summarizes it so a
fresh agent can act without that file.

## Concept: forest of fixed-size leaf-blocks

Block-structured AMR (FLASH / PARAMESH / AMReX style). The mental model:

- The domain is covered by a collection ("forest") of **equal-sized small
  blocks** — e.g. each block is an 8×8 (2-D) or 8×8×8 (3-D) patch of cells. Each
  block is an ordinary `CartesianGrid` with its own halo.
- "Forest" = a set of quadtrees (2-D) / octrees (3-D): start from a coarse root
  tiling of blocks; to refine a region, replace one block with 2ᴺ child blocks at
  half the spacing (same physical area, 2× resolution). Recurse. The roots + their
  refined descendants form a forest of trees.
- "Fixed-size leaf-blocks": every block has the **same cell count**; only the
  physical spacing changes with level (level ℓ → h₀/2^ℓ). A *leaf* is a block not
  further refined — the leaves tile the domain with no overlap and are where the
  solution actually lives.
- **Why this design** (vs a cell-based octree like p4est/Trixi): each leaf is a
  dense rectangular array, so every existing leaf operator (the `_apply_raw!`
  stencil sweep, etc.) runs **unchanged per block**. All adaptivity complexity is
  confined to the *block faces* — the coarse–fine interfaces. A cell-based octree
  puts a hanging node at nearly every cell, which would break the dense-array
  stencil sweeps the whole package is built on.
- **2:1 balance** keeps neighboring leaves within one level of each other, so a
  coarse–fine interface only ever has 3 cases (same level / one-coarser /
  one-finer) — that is what makes interface interpolation tractable.

**Docs requirement:** the final feature must ship a docs page explaining this
concept (the user asked for this explanation in both the handoff and the docs).

## Decisions & conclusions (locked with user — do not relitigate)

- **Grid = forest of fixed-size leaf-blocks**, each leaf an ordinary
  `CartesianGrid` (FLASH/PARAMESH/AMReX-octree style). Reuses 100% of
  `CartesianGrid` per block; coarse–fine handling confined to block faces.
- **Forest backend = pure-Julia serial forest in core** (Morton/Z-order keys,
  parent/child/neighbor, `refine`/`coarsen`/`balance!`). No new deps — keeps the
  Adapt/KA/LinearAlgebra/StaticArrays-only ethos. A `P4estTopology` /
  MDLA-distributed backend is **deferred** behind the `topology` + `halo_update!`
  seams.
- **2:1 balance** is the load-bearing invariant: adjacent leaves differ by ≤1
  level ⇒ coarse–fine interfaces reduce to 3 cases (same-level / one-coarser /
  one-finer). The "gold standard, not bleeding edge" choice. Rejected: cell-based
  octree (p4est/Trixi-style) — hanging nodes everywhere break dense-array leaf
  operators.
- **Block storage = vector-of-blocks first** (`Field.data` = collection of
  per-leaf padded arrays). Simplest correct path, CPU-friendly. Design the
  `for block in leaves` block-view interface so the **packed contiguous buffer**
  (one GPU kernel over all blocks, AMReX/Quokka-style) is a later drop-in
  **without touching operators**.
- **GPU is the top long-term priority — first-class, not an end-phase add-on**
  (user direction). Chosen path is *correctness-first, GPU-ready*: keep
  vector-of-blocks, but (i) the `for block in leaves` block-view interface and all
  leaf bodies stay array-level / KernelAbstractions so they are already
  device-agnostic, (ii) the packed-contiguous buffer must remain a true drop-in,
  and (iii) **GPU-parity is tested at every phase**, not just the end (see
  Gotchas). The packed buffer is structurally the same trick as NearestNeighbors'
  `data_reordered` (contiguous, tree-ordered storage — see the NN.jl reference
  section), tying GPU layout to the topology backend.
- **Operators barely change:** leaf `_apply_raw!` runs per-block unchanged. The
  new forest `apply!` = `halo_update!(forest)` → per-leaf `apply_bc!` → per-leaf
  `_apply_raw!`. The intelligence concentrates in `halo_update!` (same-level copy
  + coarse→fine interp + fine→coarse restrict at block faces).
- **R/P built once, used twice:** the coarse–fine interp/average kernels in
  `halo_update!` ARE the MG transfer stencils. `Restriction`/`Prolongation`
  leaves follow the rank-changer template (`src/operators/gradient.jl:64–82`,
  `divergence.jl`): carry both grids, override `Base.size`/`allocate_output`/
  `allocate_input`, declare `adjoint_operator` = partner.
- **MG coarse operator = rediscretization** (`laplacian(coarse_grid)`), standard
  geometric MG. Smoother = weighted Jacobi/Chebyshev, dispatched on the existing
  `isdiagonal` trait — needs a NEW `operator_diagonal(L)` (none exists; Laplacian
  diagonal = `-2·Σ_d h_d⁻²`).

## Target user-facing API (settle here)

The destination the phases build toward — **geometric** multigrid on the AMR
forest (confirmed: not algebraic MG). Type/function names are *proposed* and are
the thing to iterate on and settle. Grounded in today's real API
(`CartesianGrid(extent, ncells; bc=...)`, `laplacian`, `scalar_field`/`set!`,
`flatten`, `prepare`, `Krylov.cg` — see `src/linalg.jl:36–46`,
`examples/heat_equation.jl`); everything below the forest line is new surface.

```julia
using MatrixFreeOperators, Krylov

# Build a block-structured AMR grid (forest of fixed-size leaf-blocks)
base   = CartesianGrid(((0,1),(0,1)), (8,8); bc=((Dirichlet(),Dirichlet()),
                                                 (Dirichlet(),Dirichlet())))
forest = BlockForest(base; blocksize=(8,8), maxlevel=4)
refine!(forest, u -> indicator(u) > 0.1)   # regrid + re-establish 2:1 balance!

# Operators are constructed on the forest and run unchanged per leaf-block
L = laplacian(forest)
f = set!(scalar_field(forest), x -> source(x))

# (a) Geometric-MG preconditioner feeding Krylov
mg       = MultigridPreconditioner(L; smoother=Jacobi(2/3), cycle=:V, levels=:auto)
A        = prepare(L)
u, stats = Krylov.cg(A, flatten(f); M = mg)

# (b) ...or as a standalone iterative solver
u = solve(MultigridSolver(L; smoother=Chebyshev(2), cycle=:V), flatten(f); rtol=1e-8)

# Transfer operators are first-class operators in the same algebra
R = restriction(fine_grid, coarse_grid)    # fine  -> coarse
P = prolongation(coarse_grid, fine_grid)   # coarse -> fine   (P = Rᵀ up to scaling)
A_coarse = laplacian(coarse_grid)          # coarse operator = rediscretization
```

## What's left / next steps (risk-ordered vertical slices)

1. **Phase 0 — forest + field, no operators.** `BlockForest{N} <: AbstractGrid{N}`
   + pure-Julia topology + `refine`/`coarsen`/`balance!`; `BlockField`
   (vector-of-blocks); forest `flatten`/`flat_to_interior!`. Tests: 2:1-balance
   invariant, neighbor queries, flat↔block round-trip.
2. **Phase 1 — uniform-forest parity.** Forest `apply!` + `halo_update!` for
   **same-level neighbors only** + forest-aware `prepare`/`mul!`. Verify bit-parity
   of Laplacian/Derivative on a uniformly-refined forest vs. a single
   `CartesianGrid` of equal resolution; adjoint identity on the forest. (Retires
   plumbing risk.)
3. **Phase 2 — coarse–fine coupling (THE HARD PART).** Add coarse→fine interp +
   fine→coarse restrict to `halo_update!` + transpose `halo_update_adjoint!`.
   Verify Δ(sin kx) 2nd-order convergence preserved across a refinement interface
   (⇒ quadratic interpolation) + adjoint identity on a non-uniform forest. (Retires
   the AMR-math risk — `DESIGN.md §9` "prototype early on a small case".)
4. **Phase 3 — R/P operators + MG.** Extract Phase-2 kernels into
   `Restriction`/`Prolongation` leaves; add `operator_diagonal` +
   Jacobi/Chebyshev smoother + V-cycle driver. Solve Poisson via MG; compare to
   `Krylov.cg`.
5. **Phase 4 — AMR driver.** User-supplied refinement criterion + regrid +
   solution transfer between forests. Full adaptive solve.

## NearestNeighbors.jl indexing reference (Phase 0 input)

Studied from two sources, which agree: the package source
(`~/.julia/packages/NearestNeighbors/8wgyo/src/tree_ops.jl` + `tree_data.jl` —
**not** in the package docs, only in the source) and the author's JuliaCon
Eindhoven 2023 talk (slides at `second-brain/Software/NearestNeighbors.jl.md` +
`second-brain/Assets/`, video https://www.youtube.com/watch?v=0v_42Gqaqlw). Mine
these tricks for the Phase 0 topology backend:

- **Implicit heap-indexed array, no pointers** ("Avoid chasing pointers" slide:
  pointer chasing → cache misses; "arrays are a programmer's best friend"). Child/
  parent are pure integer arithmetic: `getleft(i)=2i`, `getright(i)=2i+1`,
  `getparent(i)=i÷2`, `isleaf(n_internal,i)= i>n_internal` (`tree_ops.jl:4–7`). The
  `KDNode` drops its `left_child`/`right_child` fields entirely. The tree *shape*
  is never stored — recomputed from a tiny `TreeData` constants struct.
- **Complete binary tree ⇒ index-derived structure** ("Size reductions" slide).
  Points are split so the tree is *complete* (all leaves full except possibly the
  last); then leaf-ness is computable from index alone and a leaf's point range
  from index + a small lookup (the `TreeData`). No holes in the array.
- **Minimal node + "recompute > store"** — the central philosophy, the highest-
  value takeaway. The `KDNode` shrinks to `split_dim` + `split_val` (≈
  `2 bytes + sizeof(T)`); the bounding box is **recreated from the parent during
  descent**, not stored. Quote: *"(Re)computing things can often be faster than
  storing and fetching from memory"* — the workload is memory-bandwidth-bound, so
  trade flops for bytes.
- **Leaf batching.** A leaf holds a contiguous *range* of `leafsize` points (not
  one point/node); `get_leaf_range` returns it via precomputed affine offsets,
  integer math only (`tree_ops.jl:78–100`). Our analogue: a block of cells.
- **Reorder for cache locality.** At build time it permutes data into
  `data_reordered` so each leaf's points are contiguous, with an index map back to
  original order; a `reordered` flag picks which to read at query time
  (`reorder_data!`, `tree_ops.jl:104–113`). This is *exactly* the packed-contiguous
  GPU buffer idea — `data_reordered ≡` AMReX's packed block buffer.
- **Transfer to our forest:**
  - *Recompute geometry from the key, don't store it per block.* Store only the
    Morton/Z-order key per leaf (level is implicit in the key) and recompute the
    block's `extent`/`spacing` from key+level — our `Grids.jl` derived accessors
    already do exactly this (`coarse block = ncells÷2, spacing×2` composes for
    free), so this philosophy is native to the codebase. Mirrors NN.jl's
    recompute-bbox-from-parent.
  - *Keep topology implicit/computed* from the keys (the dynamic generalization of
    `2i`/`2i+1`), *batch* (block of cells ≡ leaf of `leafsize` points), and store
    blocks contiguously in Morton order for the packed GPU buffer.
  - **Caveat (the user's own note flags it too):** `2i`/`2i+1` + complete-tree
    indexing only works for a *static, balanced* tree with "no holes." AMR is
    dynamic and unbalanced, so heap indexing does **not** transfer verbatim — use
    Morton keys + a sorted/hash map for neighbor/parent/child lookup. The
    recompute-from-key, minimal-node, batching, and contiguity tricks transfer
    directly.

## Gotchas / constraints

- **Adjoint correctness is the subtle part.** ⟨Lx,y⟩=⟨x,Lᵀy⟩ must hold on a
  non-uniform forest — the coarse–fine interpolation in `halo_update!` needs a
  declared transpose (`halo_update_adjoint!`), exactly mirroring
  `apply_bc!`/`fold_bc!`. Gate every phase with the adjoint identity test.
- **`halo_update!` must run ONCE over the whole forest before any per-block
  stencil** (it needs neighbor blocks' data). Don't fold it into per-block
  `apply!` the way the single-grid path does.
- **2:1 balance must be re-established after every refine/coarsen** (`balance!`),
  or coarse–fine cases beyond ±1 level appear and the stencils break.
- **Quadratic coarse–fine interpolation** is needed to preserve 2nd-order accuracy
  near interfaces; linear interpolation degrades convergence there — verify with
  the convergence-order test in Phase 2.
- Testing convention (`CLAUDE.md`): write tests per operator (action vs analytic,
  adjoint identity, composition, AD vs FD); **do not run tests unless explicitly
  told**. Test utils: `test/test_utils.jl` (`fd_gradient`, `materialize`). GPU
  parity gated behind `MFO_TEST_GPU=true` (`test/device.jl`).
- **GPU parity tested at EVERY phase, not just Phase 4** (GPU is the top priority).
  Each phase adds its forest path to the `MFO_TEST_GPU=true` parity suite so no
  CPU-only assumption accumulates in the block-view interface or kernels — the
  packed-contiguous buffer must stay a drop-in.
- No secrets involved in this work.
